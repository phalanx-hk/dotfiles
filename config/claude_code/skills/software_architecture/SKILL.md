# Software Architecture Skill

## 概要
ソフトウェア開発とアーキテクチャ設計に関する質問やタスクに対応するためのスキルセットです。4層アーキテクチャに基づき、シンプルで保守しやすいソフトウェアアーキテクチャの設計と実装を支援します。

## このスキルを使うタイミング

コード実装やファイル読み込みを開始する前に、以下のいずれかに該当する場合は必ずこのスキルを呼び出すこと。

使用条件（ユーザーが以下をリクエストした時）:
- 「コンポーネントを作成/設計/実装」
- 「コンポーネントを分離/抽出/再利用可能に」
- 「モジュール/クラスを作成/設計」
- 「アーキテクチャ設計/リファクタリング/再構成」
- 「型定義/関数設計」
- 「ディレクトリ構成/ファイル配置の決定」
- 「4層アーキテクチャ/設計原則の適用」

対象外: ドキュメント作成のみのタスク

## 4層アーキテクチャ

| 層 | 役割 |
|---|---|
| presentation | UI、API エンドポイント、CLI など外部との入出力を担う |
| application | ユースケースの調整・オーケストレーション。ビジネスロジックは持たない |
| domain | エンティティ、値オブジェクト、ビジネスルール。フレームワーク非依存。外部インフラへの依存が必要な処理（JWT 生成、パスワードハッシュ、メール送信等）のインターフェースもここで定義する |
| repository | DB・外部 API などのデータアクセスを実装する |

依存方向: `presentation → application → domain ← repository`

層間ルール:
- domain 層は他の層に依存しない
- repository 層は domain 層のインターフェースを実装する
- application 層は domain 層にのみ依存する（repository は domain に定義したインターフェースを通じて注入される）
- presentation 層は application 層のみを呼び出す

## 設計アプローチ（スキル呼び出し時の手順）

このスキルが呼び出されたら、コードを書く前に以下の順序で設計を進める：

1. domain 層を設計する（エンティティ、値オブジェクト、ビジネスルール）
2. application 層を設計する（ユースケースの入力・出力・フロー。ディレクトリは `application/` または `usecase/` を使用する）
3. repository 層を設計する（データアクセスインターフェースと実装）
4. presentation 層を設計する（エンドポイント、入力バリデーション、レスポンス形式）

## コードスタイル

### 基本原則
- ガード節：早期リターンを使用してネストを浅く保つ
- 単一責任原則（SRP）：クラスやモジュールは単一の責任を持つように設計する
- 関心の分離：異なる関心事を明確に分離する

### コメント
- WHY を説明し、WHAT は避ける
- コードから明らかな内容ではなく、なぜその実装を選択したのか、どのような背景や制約があるのかを説明する


### コード品質
- 大きな変更後は必ずリンターおよび型チェックを実行する
- ファイルは200行以内を目安とし、必要に応じて分割する

### ライブラリの取り扱い
- カスタムコードを実装する前に、可能な限り既存のライブラリを検索し、問題が解決できないか確認する
- カスタムコードの使用は、以下のケースで正当化されます
  - そのドメインに固有のビジネスロジック
  - 外部依存関係を導入するのが過剰な場合
  - ライブラリではパフォーマンス要件に満たない場合
- ライブラリの知識は最新とは限らないため、外部ライブラリを使う際は、インターフェースが極めて安定していると100%確信できる場合を除き、まずウェブ検索で最新の構文と使用法を確認する

### 命名規則
- 一般的な名称は避ける：`utils`、`common`、`shared`、`helpers`など
- isLoading, hasErrorのように補助動詞付きの説明的な名前を使用して、ブール値を表現してください
- ディレクトリ名は kebab-case を使用する（例: `user-authentication/`, `shopping-cart/`）
- 層別の配置規約: `domain/`, `application/` または `usecase/`, `repository/`, `presentation/` または `handler/`
- repository インターフェースは domain 層に定義し、実装は repository 層に置く（例: `domain/user_repository.go`, `repository/postgres_user_repository.go`）

### 関数設計
- 関数は40行以内を目安とし、それ以上長くなる場合は複数の小さな関数に分割する
- メソッド・関数の引数は 3-4 個以内を推奨とし、多い場合は引数を論理的なグループにまとめる（DI コンストラクタの引数はこの制限の対象外）
- 純粋関数を可能な限り作成し、副作用を避ける

## 設計指針

- 規模に応じて設計する：小規模なタスクでは不要な層を省略してよい。目安 — DB/外部 API を使わない単一ユースケースなら repository 層と application 層を省略可。presentation + domain の 2 層に寄せる
- 抽象化は必要になるまで導入しない：インターフェースや抽象クラスは複数実装が生じる時点で追加する（ただし repository インターフェースは依存方向を維持するため、単一実装でも domain 層に定義する）
- 高度な DDD パターン（集約、ドメインイベント、CQRS など）は明示的に要求されない限り導入しない
- ビジネスロジックはフレームワークやデータベースから分離する
- ユースケースを明確に定義し、それぞれ独立して実装する
