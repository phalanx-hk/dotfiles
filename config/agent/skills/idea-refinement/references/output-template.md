# 出力テンプレート

Phase 4 で生成する最終マークダウンの記入指針と完成例。以下 5 節を全て含むこと。

## HMW（How Might We）の作り方

形式: 「私たちはどうすれば <ターゲット> が <達成したいこと> を <制約> の中でできるようにできるだろうか？」

- ターゲット: Phase 1 で確定した対象ユーザを具体的に書く（例: 「平日 19 時以降にしか帰れない共働き世帯」）。
- 達成したいこと: 成功条件を 1 つに絞った形で書く（例: 「帰宅後 30 分で温かい夕食を食べる」）。
- 制約: 非機能要件のうち **「外したら方向性ごと崩れる」もの 1〜2 件** に絞って書く。優先順位は「コア体験を変える制約 ＞ 法規制 ＞ 期間 ＞ 予算 ＞ 人手」。複数並べると HMW が読み解きづらくなるため最大 2 件まで。

NG 例:

- **解決策混入**: 「アプリで〜」「AI が〜」のように手段が入っている。HMW は問題定義であって解決策ではない。
- **抽象すぎ**: 「人々を幸せにする」など、誰でも書ける文。ターゲットと達成したいことを具体化する。
- **制約欠如**: 制約を書かないと「全員に魔法のように届ける」のような非現実的な解しか出ない。
- **複数 HMW を並べる**: 1 つに絞る。複数あるなら方向性が違うので Phase 3 のクラスタリングからやり直す。

## 推奨方向性の書き方

- **名前**: 5〜10 字。コンセプトを表す動詞句や名詞句（例: 「冷蔵庫スワイプ献立」「家族交代シェフ制」）。
- **核心**: 1〜2 文。「誰が何をどう体験するか」を書く。機能列挙ではない。
- **なぜ推すか**: 評価根拠（実現可能性／ユーザ価値／リスクのうち決め手になった点）を 2〜3 行。

## 検証すべき／検証しない の切り分け基準

検証すべき:

- 不確実性が高く、判断を左右する仮説（外したら方向性ごと崩れる）
- ユーザに直接当てて確かめないと分からないこと（思考実験では結論が出ない）
- 投資前にチェックすべき技術リスク（実装してから「動かない」では遅い）

検証しない:

- 既知のベストプラクティスで答えが出ること
- 仮に外れても影響が小さいこと
- 検証コストが投資コストを上回ること（直接やった方が早い）

検証しないと判断したものは「理由 1 行」を必ず添える（後から見たときに判断根拠が分かるように）。

## 不明点

- 現時点で未解決の論点を最低 1 件書く。「なし」と書かない。
- 「Phase 1 で聞ききれなかった追加要件」「決めかねている分岐点」「外部依存で確定できない事項」が候補。

## 完成例（リモートワーカー向け集中支援 Web アプリ）

```markdown
# リモートワーカー向け集中支援 Web アプリの方向性

## 問題定義（HMW）

私たちはどうすれば、複数の SaaS タブと Slack 通知に注意を奪われがちな在宅勤務のフリーランス（30〜45 歳）が、1 日 3 時間以上のディープワーク時間を確保できるようにすることを、有料ツールへの追加課金なしで実現できるだろうか？

## 推奨方向性

**カレンダーブロック自動集中モード**

Google カレンダーの予定ブロックを Web アプリ（Chrome 拡張）が読み取り、ブロック開始時刻に自動で「集中モード」（業務外タブのグループ折りたたみ・Slack デスクトップ通知サスペンド・ステータスを取り込み中に変更）を発動する。ユーザはカレンダーを編集する以外の操作をしない。

なぜ推すか:

- 既存習慣（カレンダーに予定を入れる）に乗るため、追加習慣がゼロで継続率が読みやすい。
- Google Calendar API と Chrome 拡張のみで MVP を構築でき、有料 SaaS への課金が不要（制約と整合）。
- 「ブロックの実行成功率」と「ディープワーク時間の積算」がそのまま KPI になり、検証指標が明確。

## 検証すべき内容

1. **Calendar API 許諾率**: 業務カレンダーへの読み取り許諾を 50% 以上のユーザが与えるか。下回ると機能の核が動かないため、心理的障壁の実測が必須。
2. **「集中モード」の強制度合い**: タブ強制クローズと「警告のみ」のどちらが継続率を高めるか。30 名規模のパイロットで切り分ける。
3. **ディープワーク時間の自己申告と実測の乖離**: ブロック実行時間が「ユーザが集中できたと感じる時間」と一致するか。乖離が大きい場合、計測指標の再設計が必要。
4. **Slack 通知サスペンドの副作用**: 通知遮断中の重要メッセージ取りこぼしが、ユーザにどの程度許容されるか（「緊急時の解除導線」が無いと使われない可能性）。

## 検証しない内容

- **モバイル対応**: 在宅 PC が主戦場のユーザを対象とするためスコープ外。Web 拡張で機能が完結する設計と矛盾しない。
- **チーム機能（集中時間の共有・同期）**: 個人最適化を先に検証してから判断する。複雑度を持ち込むと初期検証の焦点がぼやける。
- **AI による集中時間推奨**: 既存のベストプラクティス（朝の 90 分集中など）で初期は十分。AI 機能の追加投資は早すぎる。
- **Outlook / Apple Calendar 対応**: Google Calendar 単独でユーザ層の主要セグメントをカバーできるため初期スコープから外す。

## 不明点

1. 強制クローズしたタブを緊急対応で復帰させる導線（「3 秒長押しで解除」等）の UX が未確定。誤動作・誤発火の許容線が決まっていない。
2. Slack 以外の通知系（Teams、Discord、メール）への対応範囲を MVP のどの段階で広げるか。
3. 「ディープワーク 3 時間/日」の閾値が対象ユーザの現状値より高すぎないか。事前ヒアリングで現状値の中央値を取る必要がある。
4. 計測ログのプライバシー方針（業務カレンダーの予定タイトルを保存するか、時間帯のみ保存するか）と利用規約上の表現が未整理。
5. Chrome 以外（Firefox / Edge / Safari）の拡張対応をいつ判断するか、その判断基準。
```

## 注意

- 上記の完成例は構成見本であって、正解の文面ではない。Phase 1〜3 で確定した内容に基づき、毎回新規に書く。
- 5 節の順序を変えない（読み手が探しやすいように固定）。
- 各節の見出しレベルは `##` で揃える。サブ要素のみ `###` または箇条書きで表現する。
