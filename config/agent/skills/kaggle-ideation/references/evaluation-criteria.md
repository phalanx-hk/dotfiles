# 評価基準 6 視点

Phase 3.3 で各仮説を批判的に評価する際の基準。1 仮説につき弱点を 2 つ以上明示すること。

## 視点 1: Impact カテゴリ

primary を 1 つ選び、必要に応じて任意 tags を付ける。さらに **効果見込みの根拠 1 行** を添える。

### Primary（1 つ必須）

| カテゴリ | 定義 | 適する局面 |
|---|---|---|
| `score-lift` | LB / CV を直接押し上げることを狙う | 中盤・序盤後半 |
| `robustness` | CV-LB の整合維持・public/private gap の縮小 | 中盤・終盤 |
| `diagnostic` | 直接スコアは上げないが、次手の意思決定材料を作る（adversarial AUC / OOF residual / feature importance 解析） | 序盤・中盤 |
| `ensemble-diversity` | アンサンブルに不足した予測の出方を補い、blend 後の score-lift を狙う | 中盤・終盤 |
| `metric-alignment` | 評価指標と直結したロス選択・後処理（threshold tuning / calibration / ordinal 変形） | 全フェーズ。特殊指標時は最優先 |
| `submission-strategy` | submission 残数の使い方・最終 2 つの選定・backup 確保・seed 選別 | 終盤・残 24h 未満 |

### Tags（任意、複数可）

- `low-risk`（rollback 容易、副作用小）
- `postprocess`（学習やり直し不要）
- `external-data`（規約確認必須）
- `infra-heavy`（GPU 専有や長時間学習）
- `quick-win`（30 分以内で signal が出る）
- `late-stage-only`（終盤専用）
- `early-stage-only`（序盤専用）

### 根拠カテゴリ（1 行で必須）

| 根拠 | 定義 |
|---|---|
| `過去解法` | 同 modality / 同タスク種別の過去 Top discussion / write-up / 公式 baseline で効いた事例あり |
| `理論的` | 統計的・情報理論的・最適化理論的に効くべき理由が説明できる |
| `データ観察` | 実データの EDA・OOF 解析・adversarial validation など、観察に裏付けがある |
| `仮説的（前例なし）` | 観察も先例もない着想。**この場合は (a) どの観察から生まれたか (b) 成功条件 (c) 30〜60 分の最小検証手順 (d) 失敗時に学べること、を 1 行ずつ併記必須**。観察由来を書けないなら backlog に残さず drop |

## 視点 2: 検証コスト

| 値 | 定義 |
|---|---|
| `30 分以内` | 既存パイプラインに差し替えて 1 fold 回せる |
| `数時間` | 全 fold or 中規模学習が必要 |
| `半日以上` | 大規模学習・新規実装・外部データ取得・複数 iteration が必要 |

## 視点 3: time-to-signal

「どれくらい早く良否（採用/不採用の判断）が分かるか」。検証コストと似ているが、**1 fold 回せば判明するか／全 fold まで待つ必要があるか／submit するまで分からないか** を区別する。

| 値 | 定義 |
|---|---|
| `数分` | EDA・統計量計算で判定できる（adversarial AUC、ID 統計、欠損パターン分析など） |
| `1 fold で判明` | 1 fold OOF で良否が見える（特徴量追加・ロス変更など） |
| `全 fold 必要` | fold 間分散の影響を確認しないと判断できない |
| `submit 必須` | OOF だけでは判断できず、LB 提出が必要（CV-LB 乖離検証など） |

`submit 必須` は submission 残数を消費するため、submission risk の評価と連動する。

## 視点 4: バリデーション堅牢性

| 値 | 定義 |
|---|---|
| `CV-LB 整合維持` | CV と LB が連動する設計。fold 設計・leak 防止・shift 対応が確立 |
| `過学習リスク中` | 一部 fold での偏り、target encoding の leak リスク、small fold size など |
| `リーク・分布乖離懸念` | leak 疑い・public/private 分布乖離・time-based split の崩壊リスクあり |

## 視点 5: 実装コスト

| 値 | 定義 |
|---|---|
| `既存差替え（rollback 容易）` | 既存パイプラインの 1 ステップ差し替え。失敗しても元に戻せる |
| `中規模実装` | 新規モジュール 1 個・新規学習スクリプト・依存ライブラリ追加 |
| `専門知識・外部依存` | 専門ライブラリ・大規模事前学習モデル・外部 API・人手アノテーションが必要 |

## 視点 6: submission risk

| 値 | 定義 |
|---|---|
| `低` | local 検証で完結し、submit 不要 or 1 回で済む |
| `中` | 数回の submit が必要だが残数に余裕あり |
| `高` | LB probing（特定行の正解を当てに行く）／public LB に過剰最適化／提出枠枯渇懸念。終盤は特に避ける |

## 批判的評価のガード

- **1 仮説あたり弱点を 2 つ以上明示する**（評価表に表示する数。3 つ目を内部で掘っておくとなお良いが、表示は 2〜3 で揃える）。
- **無批判表現の禁止**: 「素晴らしい」「完璧」「画期的」「最高」「革新的」「圧倒的」は出力に書かない。
- **強みは Recommended queue の選定理由内で書く**（評価表は弱点・リスクの一覧として運用し、強みカラムは設けない）。
- **「これを採用しないとしたら次に何を採るか」を 1 行で書けるか**: 書けないなら評価が浅い。
- **「仮説的（前例なし）」根拠**: 観察由来を欠くものは backlog に残さず drop。残す場合は観察由来＋成功条件＋最小検証＋失敗時の学びを併記必須。
- **「効きそう」だけで上げない**: 検証コスト・time-to-signal・submission risk の 3 つで「**今やるべき**」と言える理由を確認する。
- **leak の評価は検出・隔離視点**: leak を「使う」方向（LB only に効く加工）は private で崩れる前提で評価する。

## 評価表テンプレ

```
| # | 仮説 | カテゴリ | Impact (primary / tags) | 根拠 | Cost | time-to-signal | バリデーション堅牢性 | 実装コスト | submission risk | 弱点（2 つ以上） |
|---|------|---------|------------------------|------|------|----------------|--------------------|-----------|-----------------|-----------------|
| 1 | ... | データ健全性 | diagnostic / low-risk, quick-win | データ観察（adversarial AUC=0.85） | 30 分 | 数分 | CV-LB 整合維持 | 既存差替え | 低 | ・〜／・〜 |
| 2 | ... | ⑧学習戦略 | score-lift / late-stage-only | 過去解法（同類コンペ 1st） | 半日以上 | submit 必須 | 過学習リスク中 | 中規模実装 | 中 | ・〜／・〜 |
```

Recommended queue は「Impact カテゴリ多様性 × Cost の安さ × 依存なし × time-to-signal の速さ × submission risk の低さ」で選ぶ。終盤は重い新規学習・大規模 NN 構造変更を上位に置かない。
